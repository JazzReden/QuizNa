# Paper Exam implementation

QuizNa now offers Online Exam (the default for existing/new exams) and Paper Exam in the quiz editor. The format becomes fixed after publishing so an existing online assessment cannot change underneath its attempts. Online fullscreen, monitoring, autosave, deadline and submission behavior remains in the existing flow.

## Teacher flow

1. Create a quiz, select Paper Exam, choose its reusable section(s), and add or paste questions. Paste questions saves a new draft and opens the importer in one click after a title is entered. Paste questions is also available directly on Print & scan; Publish questions makes the changes ready without leaving that screen. Unpublished changes disable section preparation until published. Earlier printed papers remain frozen and visibly labelled. Publish before preparing sheets.
2. Open Print & scan from the exam card, editor or Sections. Choose a quiz section and click Prepare section. Named sheets are prepared from the reusable roster in last-name order, with no email entry. Open sheets are reused, saved students are skipped without creating retakes, and unregistered roster students are explicitly listed as skipped. Student accounts are required to deliver private scores to the correct dashboard. The original single-sheet backend endpoint remains for compatibility.
3. Print all section question papers and separate answer sheets together, or select a prepared student to print an individual pair. Each personalized sheet freezes the published questions, question order and choice order. Answer sheets use an A4 layout with four alignment squares and a QR identity on every page. Reprints reuse the same open sheet. Print at actual size on white paper, with dark ink and no added browser headers/footers. Keep every corner square visible.
4. After the exam, open that Paper Exam on any supported camera-equipped browser/device, sign in as its teacher, choose Use camera and Capture sheet, or upload a JPG/PNG/WebP photo. The scanner decodes the QR, checks ownership and identifies the student, exam, sheet edition and page. A page from another exam is rejected with an instruction to open the correct exam.
5. Review every answer. Multiple/faint marks are flagged and never guessed. Failed alignment leaves manual entry available. Scan each page, or enter reviewed answers manually. Written answers are transcribed by the teacher: short answers use the existing accepted-answer grading; essays use existing teacher grading after saving. This implementation does not claim handwriting recognition.
6. Confirm the review checkbox and save. Objective grading happens on the server with the printed edition's key. Use Review result & grade essays to complete written grading. Results appear in existing class lists, gradebooks, reports, CSV exports and released student results. Visible teacher dashboards, gradebooks, class lists, leaderboards and student dashboards refresh within ten seconds, on focus and on same-origin result-change events. Hidden tabs pause polling. Paper quiz cards show scanned/graded counts. New paper exams default to showing scores after saving; teachers can hold scores using existing release settings, which are never bypassed. Use Scan next sheet to continue without a false unsaved-changes prompt.

Photo processing runs in a dedicated browser worker. Images are not uploaded or retained by the server. An unfinished answer review is saved in the browser session, scoped to the signed-in teacher and sheet; restoring a review requires checking it again before saving. The draft expires after 24 hours and is removed after successful saving. Browser storage can be unavailable or full; the UI asks the teacher to keep the page open if draft storage fails. The server result remains authoritative.

## Settings and limits

- Time allowance and instructions print on the question paper. Teachers supervise timing on paper; there is no browser fullscreen/violation monitoring or automatic expiry of an offline sitting. Print preparation may happen before availability opens and recording may happen after it closes.
- Question and option randomization is stable per sheet, and the paired question paper/answer sheet always shares that order. Editing/republishing never alters issued sheets.
- Attempt limits apply when issuing and saving. There is one open sheet per student per quiz and one saved attempt per sheet. A saved sheet cannot be re-scanned into another result; corrections after saving use the existing grading page.
- All four question types are supported. Bubble recognition covers single-choice multiple-choice and true/false answers. Paper multiple-choice questions support up to eight options and exams support 1–500 questions. Long exams paginate automatically. Written answers are teacher-transcribed, not OCR.
- A student account is required for a personalized sheet. No password is printed. QR identities contain a random token and do not grant access to scores or keys; the scanning endpoint also requires the owning teacher's authenticated session.
- Camera capture requires HTTPS (or localhost), camera permission and a browser with getUserMedia/canvas/workers. Photos can be uploaded if camera access is unavailable. A phone cannot use a computer's localhost address; use the HTTPS deployment from the phone. Actual camera quality, lighting, folds, erasures and printer scaling affect recognition. The review checkbox is required even for apparently clear marks.

## Database and deployment

Local XAMPP: apply `mysql/05_paper_exams.sql` after migration 04; it was applied here without rewriting existing scores or answers. Fresh installs use the appended definitions in `mysql/schema.sql`. Local startup checks the new schema. Hosted Supabase: apply `supabase/migrations/08_paper_exams.sql` after 07 before deploying the new server. Migration 08 was tested in embedded PostgreSQL; it has not been applied to a hosted project here.

The new paper_sheets table has owner-only RLS and service-only writes. The PostgreSQL issue/save functions hold row/advisory locks, validate roles/ownership/section identity, use the existing atomic finalization/grading function and enforce idempotent submissions. Local MySQL uses its existing transaction lock and the same domain grading strategies. New exam/QR/save DTOs validate inputs, QR tokens are compared using timing-safe equality, print payloads omit keys and rubrics, unknown client score fields never influence grading, and sensitive endpoints are rate-limited. API routes refuse paper operations for online exams and online starts for paper exams. Existing published exam formats cannot change.

No new secrets or external AI service are needed. QR code generation uses qrcode 1.5.4 and reading uses jsqr 1.4.0, with pinned versions and official API documentation checked: [node-qrcode](https://github.com/soldair/node-qrcode#browser-api), [jsQR](https://github.com/cozmo/jsQR#usage). Vite builds the scanner as a same-origin worker, compatible with the existing Render script-src policy. The frontend needs camera permission when capturing; the backend's restrictive API Permissions-Policy does not control the frontend document.
